## Moderate-confidence ownership concern

This is from the other rebuilt build attempt, not the limited attempt. The final source couples complete feature readiness to presentation construction. That can make independent presentation replacement or reuse require extracting coordination later. It is a maintenance concern about the chosen responsibility boundary.

The actual reviewed lifetime is coherent: there is one authority for current data and requests, the owner ends with its presentation, late completions are guarded, and all 13 required behavior checks pass. The comparison does not demonstrate a supported-workflow failure, broken cancellation contract, required recovery gap or library defect. Nor does it establish that every asynchronous View operation needs an Application. No genuine subsequent feature-extension phase tested the predicted maintenance cost. Retain the concern at moderate confidence without upgrading it to a release blocker or changing the sealed score.

## Documentation contradictions versus reader interpretation

The frozen rebuilt corpus is consistent on the boundaries implicated by these trajectories:

- `docs/architecture.md:16–24` distinguishes local View work from feature readiness and coordinated effects; `docs/api/view.md:9–19` repeats that boundary and documents construction separately. The general permission for local asynchronous work does not contradict the feature-readiness recommendation.
- `docs/api/shared/view-bindings.md:90–98` describes explicit child-event forwarding and original event arguments. It does not promise an automatic application subscription. The limited reader repaired its wiring using supported APIs without finding a contrary contract.
- `docs/integrations/setup.md:3` explicitly makes observable data and Lit rendering independent choices. `docs/packages/data.md:5` says the data package works independently of core and the DOM. `docs/api/providers/dom.md:9–13,47` documents native string rendering. The quick start separately declares its Lit installation requirement.

Closeout identified an additional explanatory inaccuracy in the ownership-concern reader: it connected avoiding observable data with unavailable optional rendering dependencies. That dependency claim is incorrect; the data package was present, the documentation separates the choices, and the other rebuilt reader successfully used data with native rendering in the same qualified environment. The resulting implementation can still legitimately choose local fields. This is reader explanation quality and possible teaching uptake friction, not an actual contradiction in the docs or a missing framework capability. It is recorded here as supplemental interpretation; sealed assessments were not rewritten.

Both rebuilt readers spent calls investigating a rendering dependency absent from the supplied workspace. That is observable setup friction. The guide declares the dependency rather than claiming it is always present, and both readers completed working native-renderer implementations. This cohort supplied dependencies and did not evaluate registry acquisition; it cannot certify or condemn the real installation path.
