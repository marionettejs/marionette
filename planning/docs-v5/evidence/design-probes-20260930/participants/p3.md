## Stage: initial

# Document-library design

## Ownership

A library feature owner owns the successful document snapshot, current filter, per-document drafts, request status, and an activation token. It lives under the page rather than owning the page or navigation. Its list and editor are separate presentation children in separate regions. This maps naturally to a Marionette Application with child presentation owners; exact v5 application/region lifecycle APIs require verification.

The list consumes a filtered projection of the successful snapshot. A filter updates only that projection. It never reconstructs the feature shell or touches the editor region, preserving editor text, selection, and focus.

Drafts are keyed by document ID and survive editor replacement. An editor writes input into its draft immediately and submits a save intent. The feature owns that request. Closing an editor destroys only its view and subscriptions. Reopening binds to the existing draft, including saving/error status. Status updates patch the status control without rerendering the input.

Each save captures the submitted title. On success, update the successful snapshot with the server-confirmed title while retaining any subsequently typed draft. Dirty state compares draft text with confirmed text. Permit at most one save per document at a time; editing remains enabled during a save, and newer edits can be submitted after completion. Saves for different documents are independent. Errors remain visible and retryable.

A deliberate refresh sets loading status but retains successful data. Only the latest refresh may commit. Refresh reconciliation preserves local drafts and avoids overwriting title confirmations from saves completed since that refresh began; unresolved server conflicts need an explicit API concurrency contract.

Stopping the feature invalidates its activation token before destroying children and subscriptions. Late completions cannot update state or UI. Network cancellation is optional; editor closure never cancels a save. Navigation remains owned by the page and is untouched. A subsequent activation uses a fresh token and reconciles server state, since ignoring a completion cannot undo a server-side save.

## Core wiring (illustrative)

`ui` and `store` below are design adapters, **not asserted Marionette v5 APIs**. Their region, subscription, and lifecycle bindings must be checked against v5. `store.acceptRefresh` implements the reconciliation described above.

```js
let active = true, epoch = 0, refreshSeq = 0;
const current = token => active && token === epoch;
async function refresh() {
  const token = epoch, seq = ++refreshSeq;
  const baseline = store.version;
  store.setLoading(true); // Keeps the successful snapshot.
  try {
    const docs = await libraryApi.list();
    if (current(token) && seq === refreshSeq)
      store.acceptRefresh(docs, baseline);
  } catch (error) {
    if (current(token) && seq === refreshSeq) store.setLoadError(error);
  } finally {
    if (current(token) && seq === refreshSeq) store.setLoading(false);
  }
}
async function save(id) {
  const draft = store.draft(id);
  if (!active || draft.saving) return;
  const token = epoch, title = draft.text;
  store.beginSave(id);
  try {
    const result = await libraryApi.saveTitle(id, title);
    if (current(token)) store.acceptSave(id, title, result);
  } catch (error) {
    if (current(token)) store.failSave(id, error);
  }
}
const filter = value => ui.updateList(store.filtered(value));
const open = id => ui.showEditor(store.draft(id), save);
const close = () => ui.destroyEditor();
function stop() {
  active = false; ++epoch;
  ui.destroy(); store.disposeSubscriptions();
}
```

The save response shape is unspecified: `acceptSave` must follow the actual API contract, using server normalization if supplied. Initial activation calls `refresh`; whether v5 readiness should await it is an API/lifecycle detail to verify.

## Stage: revised

# Revised document-library design

Register one Library Application with the existing page using `pageApp.addChildApp('library', library)`, then explicitly await `library.start({ region: pageView.getRegion('library') })`. Navigation remains page-owned. Initial data is readiness: `prepareStart` returns `libraryApi.list()`. Marionette blocks obsolete startup results after stop, even without service cancellation. The caller handles rejected start; it awaits successful `library.stop()` before placing error presentation.

The Application owns confirmed documents, drafts keyed by ID, request status, and active-run authority. A layout View owns separate list/editor Regions. DocumentList is a CollectionView with document row Views. Filter intent calls `setFilter(predicate)`; predicates receive child Views. This replaces my initial separate filtered-projection proposal with the documented presentation API. Never rerender the layout to filter or report status.

Editor receives the retained draft model, initializes its input from it, and immediately stores each input change. Save intent belongs to the Application. Closing/replacing the editor destroys presentation only. Reopening reads the same draft and save/error state. Status bindings update only the editor's status/button controls, preserving input text and focus.

The illustrative wiring uses documented framework methods. `makeStore`, the three View classes, their intent events, and store methods are application-defined contracts, not Marionette APIs. Compatible observable-data and renderer configuration is assumed; templates and bindings are omitted.

```js
const Library = Application.extend({
  initialize() { this.data = makeStore(); },
  prepareStart() { return libraryApi.list(); },
  onStart(_app, _options, docs) {
    this.run = { valid: true, refresh: 0 };
    this.data.acceptInitial(docs);
    const layout = this.setView(new LibraryLayout());
    const list = layout.showChildView('list', new DocumentList({ collection: this.data.documents }));
    this.listenTo(list, { open: id => this.open(id) });
    this.listenTo(layout, { filter: fn => list.setFilter(fn), refresh: () => this.refresh() });
    this.showView();
  },
  open(id) {
    const editor = this.getView().showChildView('editor', new Editor({ model: this.data.draft(id) }));
    this.listenTo(editor, { save: () => this.save(id), close: () => editor.destroy() });
  },
  async save(id) {
    const run = this.run; if (!run?.valid) return;
    const edit = this.data.beginSave(id); if (!edit) return;
    try { const result = await libraryApi.saveTitle(id, edit.title);
      if (run.valid) this.data.acceptSave(id, edit, result);
    } catch (error) { if (run.valid) this.data.failSave(id, error); }
  },
  async refresh() {
    const run = this.run; if (!run?.valid) return;
    const seq = ++run.refresh, baseline = this.data.beginRefresh();
    try { const docs = await libraryApi.list();
      if (run.valid && seq === run.refresh) this.data.acceptRefresh(docs, baseline);
    } catch (error) {
      if (run.valid && seq === run.refresh) this.data.failRefresh(error);
    }
  },
  onBeforeStop() { if (this.run) this.run.valid = false; this.data.endRun(); },
  onBeforeDestroy() { if (this.run) this.run.valid = false; }
});
```

`beginSave` returns a captured title/revision or declines a duplicate in-flight save for that ID. Successful saves update confirmed data without overwriting newer draft text; failure retains drafts. The save response/normalization contract remains unverified.

`beginRefresh` retains confirmed data and records its version while marking loading. Completion clears loading, commits only the latest refresh, preserves drafts, and protects saves confirmed after that baseline. Server concurrency/conflict semantics remain unspecified. Refresh updates the existing collection; affected title changes also call the list's `filter()` when its predicate depends on titles. Refresh never uses `restart()`.

`endRun` marks pending statuses inactive. Stop invalidates requests before teardown; completions cannot change retained state or future UI. A new start reconciles server state and drafts because stopping cannot undo a server save. Regions and destroyed Views release presentation subscriptions automatically. Stop retains Application state and ordinary subscriptions to surviving sources: explicitly release any run-scoped external resources; do not blanket-clear page listeners.

**Deliberately retained:** feature-owned drafts/requests, independent list/editor lifetimes, one save per document, retained successful data during refresh, explicit late-result guards, and page-owned navigation.

## Stage: interview

# Design interview

## 1. Ownership

Required survival determined ownership. Drafts and saves must outlive editor replacement, so the feature Application owns them. The list and editor have independent presentation lifetimes, so a layout gives each a Region. Navigation must survive feature stop, so the existing page owns navigation and the registered feature child.

## 2. Passage that changed the design

`material/docs/api/collection-view.md`, **Filtering**: “Filtering controls presentation; it does not remove models or destroy their children.” Its `setFilter` contract provides the concrete operation. I replaced the initial separate filtered projection with CollectionView filtering. This fits the needed boundary without maintaining another collection. Application preparation also replaced my initially uncertain startup wiring.

## 3. Pending save, editor closure, then stop

Save captures a draft revision and marks the retained draft saving. Closing destroys the editor and releases its subscriptions; the Application, draft, document collection, and request remain alive. A completion before feature stop updates confirmed data and save status, while preserving subsequently typed draft text. A reopened editor reads this current state.

Feature stop invalidates the active-run token before teardown and marks pending statuses inactive. Marionette destroys the feature root, list, rows, and any reopened editor. The Application and retained data survive; the page and navigation remain mounted. A later save completion cannot mutate that data or UI through this handler, although the server may already have accepted it. Reopening the whole feature requires reconciliation with server state.

## 4. Helpers and omissions

The store contains substantial central behavior: draft initialization/input updates, duplicate-save suppression, revision-aware save acceptance, loading/error transitions, and refresh/save reconciliation. These are application policy rather than documented automatic Marionette behavior. Space drove their omission; the unspecified service response and concurrency contract also prevent claiming a complete reconciliation implementation. View templates and observable bindings were omitted for space, with provider setup assumed.

## 5. Alternatives

A View-owned save suits an edit whose work need not survive View destruction. A separate surviving nonvisual owner could share drafts across features; this task only needs the feature lifetime. A projected collection could suit consumers that need filtered data independently of presentation. Restart suits intentionally rebuilding the feature, but would violate this refresh requirement. I retained one pending save per document; ordered queues or versioned concurrent writes would require an explicit service contract and product need.

## 6. Hardest statement to apply

Recollection: `material/docs/api/application.md`, **Lifecycle methods and results**, says ordinary stop keeps the Application active during preparation. That makes `isRunning()` alone insufficient for immediate completion invalidation, motivating `onBeforeStop` and a separate token. Speculation remains around server reconciliation, not that documented lifecycle timing.

## Stage: counterfactual

# Prompted counterfactual comparison

This comparison is prompted by the follow-up; it is not evidence of a spontaneous initial comparison.

**Marionette Application best fits these requirements.** Initial readiness and independently stopping the feature, while preserving the surrounding page, match its documented lifecycle. Its retained instance can own drafts and operations across editor replacement.

A **retained root View** could own drafts and save requests while separate Regions isolate list/editor updates. However, this task also requires stopping the whole feature and rejecting obsolete completions. Making that View reusable across stop/start would require a custom lifecycle or another surviving owner.

A **plain controller** could implement all of this, but would need to establish root ownership, cancellation of obsolete startup activation, and teardown coordination itself. I would choose one if integration required a lifecycle incompatible with Application or the project already had an equivalent owner.

**Application removes** custom initial-start coordination, protection against obsolete preparation activating UI, root teardown on stop, and registered parent/child lifetime coordination. Regions and Views—not Application alone—supply child replacement and presentation subscription cleanup.

**Custom logic remains:** retained drafts, captured save revisions, save-status transitions, per-document concurrency policy, latest-refresh selection, refresh/save reconciliation, and invalidation of requests started after preparation. Server acceptance cannot be undone by stopping UI.

The explicit ownership question encouraged a lifecycle-centered explanation. The 35-line limit made a conceptual answer easier to present but hid substantial product work in store helpers and prose. A product ticket would also require concrete templates, bindings, error states, API contracts, and verification of focus and concurrent completions.

**A View would suffice** if this were an always-mounted page panel receiving already-loaded documents, with saves allowed to end with the editor and no independent stop/restart or retained draft requirement. Its local model, input handlers, and Regions could then own the entire interaction.
