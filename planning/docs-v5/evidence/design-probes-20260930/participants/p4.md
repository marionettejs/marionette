# Document library design

**Ownership.** A feature-scoped `LibraryApplication` owns the document collection, drafts keyed by document ID, load state, save state, and requests. Each draft holds text, a revision, and save status. Drafts survive closing or replacing their editor. The application's layout owns separate list and editor regions; its collection view owns document rows. Existing page navigation belongs to the surrounding application and remains running.

The editor writes input directly into its draft model. Filtering changes only the list's visible items; it never renders the layout or editor. Draft/status changes update individual editor controls rather than replacing the input. Reopening binds a new editor to the same draft, including pending or failed save status.

**Requests.** List responses update server data without overwriting existing drafts. A deliberate refresh retains the existing collection while showing loading/error state. A request sequence rejects obsolete list responses. Save requests belong to the application, not the editor. Allow one pending save per document; users may continue editing, but another save waits until completion. A successful save marks only the captured draft revision as saved, so edits made during the request stay dirty. Assume `saveTitle` accepts the submitted title; any server-normalized title needs an explicit response contract.

**Cleanup.** Stopping the feature invalidates its request epoch before removing its UI and scoped subscriptions. Completions from that epoch do nothing, even if the API cannot cancel the actual network operation. Destroyed editors release their bindings, never the application's save requests. No global router shutdown or broad event-bus cleanup.

Below is illustrative application-owned wiring, not runnable implementation. `ui`, `drafts`, and `docs` are local adapters. Exact Marionette v5 application lifecycle hooks, region teardown, and collection-view filtering APIs are **uncertain** and must be checked before implementation. Map `start`/`stop` to those verified lifecycle hooks; do not treat these names as confirmed v5 APIs.

```js
class LibraryApplication { // Mn.Application integration: uncertain
  epoch = 0; loadSeq = 0; active = false;
  start() { this.active = true; this.epoch++; ui.mount(); this.refresh(); }
  stop() {
    this.active = false; this.epoch++; ui.dispose();
    drafts.clearPending(); // retain text; old completions cannot change it
  }
  live(epoch) { return this.active && this.epoch === epoch; }
  filter(query) { ui.filterList(query); } // editor region is untouched
  open(id) { ui.showEditor(drafts.getOrCreate(id, docs.get(id))); }
  close() { ui.emptyEditor(); } // no request ownership here
  async refresh() {
    const epoch = this.epoch, seq = ++this.loadSeq;
    const current = () => this.live(epoch) && seq === this.loadSeq;
    ui.loadState('loading'); // retain docs
    try {
      const data = await libraryApi.list();
      if (current()) { docs.replace(data); ui.loadState('ready'); }
    } catch (error) { if (current()) ui.loadState('error', error); }
  }
  async save(id) {
    if (!this.active) return;
    const draft = drafts.get(id);
    if (draft.pending) return;
    const epoch = this.epoch, { text, revision } = draft.snapshot();
    draft.beginSave();
    try {
      await libraryApi.saveTitle(id, text);
      if (this.live(epoch)) draft.saved(revision, text, docs);
    } catch (error) { if (this.live(epoch)) draft.failed(error); }
  }
}
```

The editor emits save intent to its application; its close event affects only its region. The list emits open intent to that same owner. UI subscriptions use framework-scoped listening and are disposed with their owners. `draft.saved` updates the document's server title and saved revision without changing current editor text or focus.

## Stage: revised

# Document library design

**Owners.** `LibraryApplication` owns documents, the filtered collection, drafts keyed by ID, and requests. A `Shell` View owns list/editor Regions; `Rows` is a CollectionView of document Views. Editor Views borrow draft Models. The existing page navigator remains owned by its current application.

**Initial loading and refresh.** Show the shell in `onBeforeStart`; return initial data from `prepareStart`; commit it in synchronous `onStart`. Marionette suppresses obsolete readiness completions. An initial failure activates a retry screen. Explicit refresh uses the documented application helper `createLatestRequest`, retaining successful data while loading or failing. It is application code, not a Marionette export. No filter or refresh calls `restart`.

**Drafts and saves.** Input events immediately update retained draft text and revision. Editor status bindings update controls without rerendering the input. Opening reads that same draft/status Model. A save captures its revision, allows continued typing, and permits only one write per document at a time. Success updates the server title and saved revision without overwriting newer text; failure retains the draft. Completion permission belongs to the feature run, not the editor. Closing/replacing the editor cannot cancel a save or prevent retained-state reconciliation.

**Illustration.** `Shell`, `Rows`, and `Editor` are ordinary View/CollectionView subclasses omitted for space. Shell forwards semantic events with the payloads below; editor input uses `events`, status uses `modelEvents`, and child intent uses `childViewEvents`/`childViewTriggers`. `draftFor`, `beginSave`, `finishSave`, `failSave`, `filterRows`, and `commitRows` are application-specific pseudocode, not framework APIs. Configure `DataApi` once during setup. No signal argument is assumed for either supplied API.

```js
import { Application, setDataApi } from 'marionette';
import { Collection, DataApi } from '@mnjs/data';
setDataApi(DataApi);
const LibraryApplication = Application.extend({
  initialize() { this.docs = new Collection(); this.rows = new Collection(); this.drafts = new Map(); },
  onBeforeStart() {
    this.invalidate(); const old = this.getView(); if (old) this.stopListening(old);
    this.run = {}; const shell = new Shell(); this.showView(shell);
    shell.showChildView('list', new Rows({ collection: this.rows }));
    this.listenTo(shell, 'filter', q => filterRows(this, q));
    this.listenTo(shell, 'open', id => shell.showChildView('editor', new Editor({ model: draftFor(this, id) })));
    this.listenTo(shell, 'close', () => shell.getRegion('editor').empty());
    this.listenTo(shell, 'save', id => void this.save(id).catch(reportError));
    this.listenTo(shell, 'refresh', () => { if (this.isRunning()) { shell.loading(); void this.reads.run().catch(reportError); } });
    this.listenTo(shell, 'before:destroy', () => { this.invalidate(); this.stopListening(shell); });
  },
  async prepareStart() { try { return { rows: await libraryApi.list() }; } catch (error) { return { error }; } },
  onStart(app, options, result) {
    this.reads?.dispose();
    if (result.error) this.getView().failed(result.error); else commitRows(this, result.rows);
    this.reads = createLatestRequest({ load: () => libraryApi.list(), commit: rows => commitRows(this, rows), fail: error => this.getView().failed(error) });
  },
  async save(id) {
    if (!this.isRunning()) return;
    const draft = draftFor(this, id); if (draft.get('pending')) return;
    const run = this.run, ticket = beginSave(draft);
    const current = () => this.run === run && this.isRunning();
    try { await libraryApi.saveTitle(id, ticket.text); }
    catch (error) { if (current()) failSave(draft, ticket, error); return; }
    if (current()) finishSave(this.docs, draft, ticket);
  },
  invalidate() { this.run = undefined; this.reads?.dispose(); },
  onStop() { this.invalidate(); }, onBeforeDestroy() { this.invalidate(); },
  onDestroy() { this.docs.destroy(); this.rows.destroy(); for (const draft of this.drafts.values()) draft.destroy(); }
});
```

`commitRows` updates records and filtered membership using Collection operations; `filterRows` touches only list membership. Neither replaces the shell/editor. Stop destroys the owned UI and invalidates completions; ordinary `listenTo` survives stop, so remove bindings to replaced roots explicitly. Destruction releases owned sources. A later activation must reconcile obsolete pending-save status before allowing another write; stopping cannot prove server rollback.

**Deliberately retained:** feature-owned drafts/requests, separate presentation regions, revision-aware saves, last-successful refresh data, scoped cleanup, and independent navigation. Replaced the custom lifecycle and UI disposal adapter with framework ownership.

## Stage: interview

# Design interview

## 1. What determined the owners?

Required lifetimes determined ownership. Drafts and saves must outlive individual editors, so the feature owns them. The editor owns its input and status presentation. Separate Regions let filtering change the list without touching editor DOM. The feature Application owns activation and initial readiness; its refresh controller owns independently replaceable reads. Existing navigation has a longer, separate lifetime.

## 2. Most influential passage

`material/docs/application-composition.md`, “Choose the owner before writing the async function”: “Begin with `prepareStart`; depart from it only when the operation has a different lifetime.”

This changed the initial custom `start()`/`stop()` sketch into `Application.extend`, with `onBeforeStart`, `prepareStart`, and `onStart`. Initial loading became readiness; deliberate refresh remained an active-feature operation. The surrounding owner table made that distinction concrete.

## 3. Editor closure, save completion, and feature stop

Closing the editor empties its Region and destroys its View and managed UI bindings. The feature, draft Model, save status, and transport promise remain alive. Reopening binds a new editor to that same Model.

If the save settles before feature stop, the feature reconciles the captured revision and status even with no editor displayed. Newer edits remain intact. If feature stop succeeds first, Marionette destroys the feature UI, and `onStop` invalidates its run token and disposes refresh requests. The transport may still complete, but its completion cannot update retained Models or UI. Collections and drafts survive ordinary stop and are released on terminal destruction. The sketch leaves subsequent reconciliation of obsolete pending status in prose.

## 4. Central omitted behavior

Revision-aware draft reconciliation, per-document save locking, and targeted editor bindings are helpers/prose. Space was the main reason; these are application policies rather than missing framework APIs. However, reactivation after an unobserved save remains underspecified: the code alone does not establish correct pending-status recovery. That is a design limitation, not a verified implementation.

## 5. Alternatives

I considered a custom feature lifecycle, replaced after reading the native readiness contract. A child Application would fit an editor with independent asynchronous readiness; this editor only needs a View bound to retained state. Editor-owned saving would fit a product that explicitly cancels editing work on closure, which conflicts with this task. Concurrent writes would require a server version/conflict contract; serialization is sufficient here.

## 6. Hardest statement to apply

Recollection: `application-effects.md`, “Reconcile retained drafts before suppressing UI,” requires reconciliation above disposable editors. Distinguishing editor disappearance from whole-feature deactivation was hardest. My interpretation is that reconciliation continues across editor closure but stops at feature deactivation. Whether later restart should reconcile through a longer-lived session owner is an unresolved product choice, not a documented guarantee.

## Stage: counterfactual

# Prompted counterfactual comparison

This comparison was explicitly prompted; it is not evidence of my spontaneous initial choice.

**Marionette Application is the best fit for the stated task.** The feature has initial asynchronous readiness, a whole-feature stop boundary, retained data, and requests whose lifetimes differ from disposable editors. Application supplies a coherent activation and ownership boundary around a retained root View.

A retained root View can preserve editor DOM during list changes, but that alone does not coordinate readiness or distinguish editor closure from feature deactivation. A plain controller could implement everything, but would need its own start/stop rules, root ownership, cancellation boundaries, and cleanup integration. My initial sketch effectively took that route; the supplied documentation led me to use the existing framework contracts.

**Application removes** custom initial-readiness orchestration, suppression of obsolete startup completion, and manual destruction of its owned UI on successful stop. It also provides public hooks and scoped listening for integrating the feature with its parent.

**Custom logic remains:** draft storage and edit revisions; per-document save serialization; completion permission across feature runs; refresh ordering and disposal; retained successful data; filtered membership; targeted input/status updates; and recovery of a pending save whose completion became inactive. Application does not automatically give user-event promises these semantics or cancel server writes.

**Exercise effects.** Asking explicitly for owners made lifetime boundaries more prominent than they might be in an ordinary product ticket. The short code limit encouraged helpers and prose, exposing architecture while concealing implementation work—especially status reconciliation after stop. A product implementation would need concrete bindings, service contracts, and behavioral verification.

**A View would suffice** if the parent supplied ready data and owned all draft/save/refresh state, while this feature only displayed that state and emitted edit/filter/save intentions. Its Region could then own placement and destruction without another Application.
