## Stage: initial

# Document-library design

Use a feature-scoped owner with two independent presentation regions: a document list and an editor. The surrounding page owns navigation and the feature’s mounting region. Stopping this feature affects only that region and its children.

**Data and requests:** The feature owns the last successful document collection, list-request state, and a persistent session model per document: draft title, revision, save status, and error. Sessions live beyond any individual editor. The feature owns saves; editor views only request them. Permit one pending save per document, while still allowing draft edits. A save acknowledges its captured revision without replacing newer text. Reopening binds to the same session and displays its current status.

**Presentation:** A CollectionView presents a filtered projection of the successful collection. Filtering changes only that projection; it never reconstructs the feature layout or editor. The editor updates its session on input. Status changes update a dedicated status element without rendering the input again, preserving selection and focus. Closing/replacing destroys the editor view and its subscriptions, but leaves the session and save alone.

**Refresh:** Keep the successful collection visible while another list request runs. Commit only the latest request’s successful result. Failure preserves the collection and displays an error. Refresh does not overwrite an existing editor session; unsaved drafts remain authoritative for editing.

**Cleanup:** Stopping invalidates a feature generation before destroying its owned presentation. Every asynchronous completion checks that generation. List requests can additionally be aborted if the API supports it; saves may finish remotely, but cannot update stopped UI or state. A later start gets a new generation. Never destroy the surrounding page or its navigation listeners.

The following is illustrative coordinator wiring, not verified Marionette v5 syntax. `ui`, `state`, and `sessions` are application-defined adapters. Their methods describe responsibilities, not framework APIs. Bind `start`/`stop` to the actual feature lifecycle after verifying the v5 hooks; `Application`, `CollectionView`, region operations, and lifecycle hook names require verification.

```javascript
let active = false, generation = 0, listRequest = 0;
const current = g => active && generation === g;
function start() { active = true; generation++; ui.mount(); refresh(); }
function stop() {
  active = false; generation++; ui.destroyOwnedViews();
  sessions.markPendingInactive();
}
async function refresh() {
  const g = generation, request = ++listRequest;
  state.setListStatus('loading');
  try {
    const documents = await libraryApi.list();
    if (!current(g) || request !== listRequest) return;
    state.replaceSuccessfulDocuments(documents);
    state.setListStatus('ready');
  } catch (error) {
    if (current(g) && request === listRequest) state.setListError(error);
  }
}
function filter(query) { ui.list.setFilter(query); }
function open(id) { ui.editor.show(sessions.getOrCreate(id, state)); }
function close() { ui.editor.empty(); }
async function save(id) {
  const session = sessions.get(id);
  if (!active || session.isSaving()) return;
  const g = generation, { title, revision } = session.snapshotDraft();
  session.beginSave();
  try {
    await libraryApi.saveTitle(id, title);
    if (!current(g)) return;
    session.acknowledgeSavedRevision(revision, title);
  } catch (error) {
    if (current(g)) session.failSave(error);
  }
}
```

`acknowledgeSavedRevision` records the persisted title, updates the corresponding list model, and reports either saved or remaining unsaved changes. Request reconciliation needs care if a concurrent list response contains an older title: do not let that response overwrite a save acknowledged after the list request began.

## Stage: revised

# Document-library design

Use a `Library` Application in the existing page's library Region. It owns records, retained editor sessions, requests, and activation. The page continues owning navigation. Initial loading belongs in `prepareStart`; refresh is an explicit operation that retains the shell and last successful records.

The shell has separate list/editor Regions. A CollectionView borrows a filtered collection; filtering updates that collection without touching the editor. Each editor borrows a persistent session model containing draft, edit identity, and save status. Input events update that model; status events update only status controls. Reopening seeds the input from the session. Region replacement destroys editor presentation and subscriptions, not the session or save.

Save one request per document at a time, allowing newer edits while saving. Reconcile the captured draft identity and persisted title in the feature owner, even when the initiating editor has gone. A changed draft remains dirty. Completion permission depends on the library root, not the editor. Stopping destroys that root, disposes refresh requests, and makes pending completion handlers inert; transport may still finish remotely.

```javascript
import { Application, View, CollectionView, setDataApi, setStateApi } from 'marionette';
import { Collection, Model, DataApi, StateApi } from '@mnjs/data';
setDataApi(DataApi); setStateApi(StateApi);
const Shell = View.extend({ template: () => '<section class="list"></section><section class="editor"></section>', regions: { list: '.list', editor: '.editor' } });
const Library = Application.extend({
  initialize() { this.records = new Collection(); this.visible = new Collection(); this.sessions = createSessions(); },
  createState() { return new Model({ status: 'loading' }); },
  onBeforeStart() {
    this.reads?.dispose(); const shell = new Shell({ state: this.getState() });
    this.listenTo(shell, 'before:destroy', () => { this.reads?.dispose(); this.stopListening(shell); });
    this.listenTo(shell, 'open', id => shell.showChildView('editor', new Editor({ model: this.sessions.forRecord(id, this.records) })));
    this.listenTo(shell, 'close', () => shell.getRegion('editor').empty());
    this.listenTo(shell, 'save', id => { void this.save(id).catch(reportError); });
    this.listenTo(shell, 'filter', query => projectFilter(this.records, this.visible, query));
    this.listenTo(shell, 'refresh', () => { void this.refresh().catch(reportError); });
    this.showView(shell); shell.showChildView('list', new CollectionView({ collection: this.visible, childView: Row }));
  },
  prepareStart() { return libraryApi.list(); },
  onStart(app, options, rows) { this.commit(rows); this.reads = createLatestRequest({ load: () => libraryApi.list(), commit: rows => this.commit(rows), fail: error => this.getState().set({ status: 'error', error }) }); },
  refresh() { if (!this.isRunning() || this.getView()?.isDestroyed()) return Promise.resolve(false); this.getState().set('status', 'loading'); return this.reads.run(); },
  async save(id) {
    const root = this.getView(), session = this.sessions.get(id);
    if (!this.isRunning() || !root || root.isDestroyed() || session.isSaving()) return;
    const draft = session.beginSave();
    const current = () => this.isRunning() && this.getView() === root && !root.isDestroyed();
    try { await libraryApi.saveTitle(id, draft.title); }
    catch (error) { if (current()) session.failSave(error); return; }
    if (current()) session.acknowledge(draft, this.records);
  },
  onStop() { this.reads?.dispose(); this.sessions.markPendingInactive(); },
  onBeforeDestroy() { this.reads?.dispose(); },
  onDestroy() { this.visible.destroy(); this.records.destroy(); this.sessions.destroy(); }
});
const library = new Library({ region: page.getRegion('library') });
await library.start(); // Later: await library.stop(); navigation remains owned by page.
```

**Illustrative omissions:** `Row`, `Editor`, shell controls/intent forwarding, `createSessions`, `projectFilter`, `commit`, and `reportError` are application code. `createLatestRequest` is the documented application helper, not a Marionette export. `commit` updates records/projection and ready status while preserving drafts and newer acknowledged saves. Use identity-preserving collection operations. Configure forwarding with `childViewTriggers`/`childViewEvents`; editor `modelEvents` must not rerender its input. Native preparation suppresses obsolete initial results even though this API does not accept an abort signal. Handle startup rejection at the page boundary. No code was executed or tested.

## Stage: interview

# Design interview

## 1. Chosen owners

Required lifetimes determined ownership. The Library Application outlives editor replacement and coordinates startup, records, retained drafts, and saves. Regions own disposable presentation; CollectionView owns repeated rows. The existing page owns navigation. Separate list/editor Regions make filter updates independent of editor text and focus.

## 2. Passage that changed the design

`material/docs/application-composition.md`, “Choose the owner before writing the async function”: “Begin with `prepareStart`; depart from it only when the operation has a different lifetime.” This replaced my initial manual start/generation coordinator with Application preparation for the first load. The same section's explicit-refresh distinction kept subsequent refreshes outside startup. These were concrete changes, rather than merely verified names.

## 3. Editor closure, then feature stop

Closing empties the editor Region and destroys the editor and its presentation subscriptions. The library root, session model, captured draft, and service promise remain alive. If the save completes while Library remains active, its owner acknowledges the captured draft, updates persisted title/status, and preserves any newer draft. Reopening reads that retained session.

If Library stops first, its root and descendant Views are destroyed. Refresh disposal suppresses late reads. The session store remains owned by the Application object; `markPendingInactive` changes pending status at stop. The save's transport can finish, but the root-identity/running checks prevent its later success or failure from mutating feature state. Terminal Application destruction releases owned collections and sessions. Page navigation remains alive.

Restart reconciliation of an inactive save whose server outcome is unknown needs an explicit policy; my excerpt does not fully specify it.

## 4. Important omitted behavior

Draft-identity reconciliation, observable save status, and stale-refresh versus acknowledged-save merging remain session/commit helpers. Space drove this omission; these are application policies, not identified framework API gaps. Editor input/status handling and intent forwarding are also described rather than implemented. Consequently, the excerpt cannot independently demonstrate every required behavior.

## 5. Alternatives

An editor-owned request is appropriate when replacing that editor should abandon its entire workflow; it conflicts with this task. A child Editor Application would fit independent asynchronous editor readiness. Ordinary Views suffice here. A longer-lived persistence store would fit drafts that must reconcile across complete Library stop/restart; my design guarantees retention across editor replacement within the feature.

## 6. Hardest statement to apply

From my recorded reading, `material/docs/application-effects.md`, “Reconcile retained drafts before suppressing UI,” says to reconcile even when no screen can show success. Applying that alongside this task's inactive completions after whole-feature stop was hardest. My interpretation distinguishes editor destruction from feature deactivation. Whether reconciliation should continue after feature stop is a product-policy question; claiming the docs settle that exact requirement would be speculation.

## Stage: counterfactual

# Prompted counterfactual comparison

This comparison was explicitly requested after the design exercise; it was not my spontaneous initial choice.

**Marionette Application best fits the stated task.** The feature has initial asynchronous readiness, an active lifetime, owned presentation, and completion rules that extend beyond an individual editor. A retained root View provides presentation continuity but does not by itself coordinate those feature transitions. A plain controller can implement them, as my initial design outlined, but must supply the lifecycle and presentation ownership arrangements itself.

Application removes my hand-written startup/stop coordinator: `prepareStart` supplies readiness and obsolete-start suppression, its Region owns the root View, and successful stop destroys that presentation. Lifecycle hooks provide places to release refresh requests and terminally owned data. It does not automatically cancel arbitrary service promises or make every subscription active-run scoped.

Custom logic remains substantial: persistent per-document sessions, edit identities, observable save status, one pending save per document, reconciliation of saved versus newer draft text, filter projection, refresh ordering, refresh/save conflict policy, and completion permission tied to the library root. Application does not decide these policies. The latest-request helper is application code.

**The exercise shaped the answer.** Asking explicitly for owners made lifetimes and cleanup unusually prominent. The code limit encouraged compressed wiring and omitted central helpers, making it easier to communicate structure but harder to judge completeness. A product ticket would require inspecting existing integrations, implementing those helpers and event paths, and verifying actual focus preservation and late-completion behavior.

**A View would suffice** if the feature instead received already-loaded records, made synchronous local title edits, and discarded drafts when its Region was emptied. With asynchronous requests and independent save lifetimes removed, a View with child Regions and a CollectionView could own the remaining presentation directly.
