## Stage: initial

# Document-library feature

**Ownership.** A feature application/controller owns the last successful document collection, per-document drafts and save state, and request bookkeeping. A draft contains its text, save status, and save sequence. These survive editor destruction for the lifetime of the feature. The API adapter performs network requests; views do not own requests.

A feature layout contains separate list and editor regions. The list is a filtered presentation of the retained document collection. Filtering updates only that region. An editor reads its draft when opened and writes input changes immediately into that draft. Save-status notifications update only status controls, preserving the input element, selection, and focus. Closing or replacing an editor destroys its view and subscriptions but leaves its draft and pending save intact.

**Requests.** Refresh sets loading state without clearing successful data. A refresh sequence rejects superseded responses. A save captures submitted text and uses a per-document sequence to reject older completions. Success records what was saved without overwriting text typed afterward; the UI can distinguish “saved” from “unsaved changes.” If overlapping saves are permitted, the API must guarantee write ordering; otherwise serialize saves per document. In this sketch a pending save disables another save for that document.

**Cleanup.** Feature stop invalidates a lifetime token, destroys only its layout, and releases its subscriptions. All pending completions check the token before touching local state or UI. Editor closure never aborts a save. The outer page and its navigation remain owned by their existing application and are never destroyed or globally unbound.

The JavaScript below illustrates ownership and guards, **not verified Marionette v5 signatures**. `mountLayout`, region helpers, and `render*`/`notifyDraft` are explicit placeholders. Verify the v5 application start/stop hooks and region APIs before implementation. `notifyDraft` emits a scoped state event; each editor unsubscribes when destroyed.

```js
let live = false, epoch = 0, refreshSeq = 0, documents = [], layout;
const drafts = new Map();
const active = token => live && token === epoch;
function draft(id) {
  if (!drafts.has(id)) drafts.set(id, {
    text: documents.find(d => d.id === id).title, status: 'idle', seq: 0
  });
  return drafts.get(id);
}
function start() { live = true; ++epoch; layout = mountLayout(); refresh(); }
function stop() { live = false; ++epoch; layout.destroy(); releaseFeatureSubscriptions(); }
function filter(query) { renderFilteredList(layout, documents, query); }
function open(id) { showEditorRegion(layout, id, draft(id), { input, save }); }
function close() { emptyEditorRegion(layout); }
function input(id, text) { draft(id).text = text; }
async function refresh() {
  const token = epoch, request = ++refreshSeq;
  renderListStatus(layout, 'loading');
  try {
    const result = await libraryApi.list();
    if (!active(token) || request !== refreshSeq) return;
    documents = result; renderCurrentFilter(layout, documents);
    renderListStatus(layout, 'ready');
  } catch (error) {
    if (active(token) && request === refreshSeq) renderListError(layout, error);
  }
}
async function save(id) {
  const d = draft(id), token = epoch, text = d.text;
  if (d.status === 'saving') return;
  const request = ++d.seq; d.status = 'saving'; notifyDraft(id);
  try { await libraryApi.saveTitle(id, text);
    if (active(token) && request === d.seq) recordSaved(id, text);
  } catch (error) { if (active(token) && request === d.seq) recordSaveError(id, error); }
}
```

`recordSaved` updates the document's confirmed title, stores the submitted text as the draft's saved baseline, and notifies list/status presenters. It never replaces current draft text. `recordSaveError` retains the draft and exposes retryable error state. Refresh results never overwrite existing drafts. Lifecycle integration must initialize new feature state on a fresh start so an inactive pending save cannot leave a restarted feature stuck in “saving.”

# Revised document-library design

Use a **LibraryApplication registered under the existing page Application**. It owns successful document data, retained drafts/save status, and API operations. Its root View owns separate list and editor Regions; a CollectionView owns document rows. Existing navigation belongs to the page and survives stopping the child.

Initial readiness belongs in `prepareStart`. Return `libraryApi.list()` and consume its result in `onStart`; Marionette prevents cancelled preparation from activating even if this API cannot accept a signal. Later refresh/save operations need their own run and request guards: the preparation signal does not cover them.

Filter with `CollectionView.setFilter`, never by rendering the layout. Closing/replacing the editor replaces only its Region. Editors initialize from the current retained draft, report input immediately, and observe save-status changes through scoped subscriptions. Status updates change only the editor's own status/button controls, preserving its input element and focus.

```js
import { Application, CollectionView, View } from 'marionette';
const Layout = View.extend({
  template: layoutTemplate, regions: { list: '.list', editor: '.editor' }
});
const List = CollectionView.extend({ childView: DocumentRow });
const LibraryApplication = Application.extend({
  initialize() { this.drafts = new Map(); this.run = 0; this.refreshSeq = 0; },
  prepareStart() { return libraryApi.list(); },
  onStart(_app, _options, documents) {
    ++this.run; this.documents = documents;
    const root = this.setView(new Layout());
    this.list = new List({ collection: documents });
    root.showChildView('list', this.list);
    this.listenTo(root, {
      open: id => this.open(id), close: () => this.close(),
      filter: query => this.filter(query), refresh: () => this.refresh()
    });
    this.showView();
  },
  filter(query) { this.list.setFilter(row => row.model.title.includes(query)); },
  open(id) {
    const editor = new Editor({ state: ensureDraft(this, id) });
    this.listenTo(editor, {
      input: title => updateDraft(this, id, title), save: () => this.save(id)
    });
    this.getView().showChildView('editor', editor);
  },
  close() { this.getView().showChildView('editor', new EmptyEditor()); },
  refresh() { return guardedRefresh(this); },
  save(id) { return guardedSave(this, id); },
  onBeforeStop() { ++this.run; markUnconfirmedSaves(this); }
});
const library = pageApplication.addChildApp('library', new LibraryApplication());
try { await library.start({ region: pageContentRegion }); }
catch (error) { await library.stop(); showStartError(error); }
```

**Illustrative boundaries.** Templates, View classes, event names/payloads, and helpers are application-defined pseudocode. Configure a compatible renderer and StateApi; `ensureDraft` returns the same observable draft source on reopening. This sketch uses the documented default plain-array DataApi. Layout/row event forwarding is omitted and must honor the shown application event contracts.

`guardedRefresh` retains successful data while showing loading/error status in a separate bounded presentation. Capture `run` and an increasing refresh sequence; commit only when both match and `isRunning()` is true. Success replaces only the list Region with a newly wired List using the current filter; preserve all drafts and the editor.

`guardedSave` captures draft text and `run`, permits one pending save per document, and calls `libraryApi.saveTitle(id, text)`. Closing the editor never cancels it. Valid completion updates the confirmed document title, saved baseline, and observable status without replacing newer draft text. Failure preserves text and exposes retry. Recompute title-dependent filtering after success. Refreshes overlapping saves must not overwrite newer confirmed titles: invalidate/retry that refresh or merge protected records.

**Cleanup and retained decisions.** Keep initial draft ownership, bounded presentation updates, serialized saves, and obsolete-completion guards. Replace manual initial-load tokens with framework preparation. Region replacement and root teardown destroy Views and release subscriptions; do not broadly clear Application subscriptions on stop. Stop invalidates later operations and destroys only feature UI. Drafts remain; interrupted saves become “outcome unconfirmed” for a future start. Permanent Application destruction ends retained-state ownership. No tests or application implementation were performed.

## Stage: interview

# Design interview

## 1. What determined the owners?

Required survival determined ownership. Drafts and saves must outlive an editor, so the feature Application owns them. The editor owns input presentation and local subscriptions. The layout's Regions own replaceable panels; CollectionView owns rows. The existing page owns navigation and the registered feature child because navigation must outlive feature stop.

## 2. Most influential passage

`material/docs/records.md`, **Prepare, then display**: “The Application needs no separate run flag or request controller for this initial load.”

This changed my initial manual startup controller into `prepareStart()` returning the API result and `onStart()` composing the UI. I retained guards for later refresh/save operations because `material/docs/api/application.md`, **Operations after start**, explicitly assigns their concurrency and lifetime policy to application code.

## 3. Closure, pending save, then stop

Closing the editor replaces its Region content, destroying the editor and its subscriptions. The Application, documents, draft source, and save remain alive. A valid save completion updates confirmed title, saved baseline, and status; it preserves any newer draft text. Reopening reads that same source and its current status.

Feature stop advances the run token and marks outstanding save outcomes unconfirmed. Application stop destroys the feature root, list, rows, and any editor. The Application instance and retained drafts remain; the page and navigation remain mounted. A later save response cannot mutate local state because its token is obsolete. The remote write may still finish; stop does not undo it. A future start must reconcile that uncertainty.

## 4. Central behavior omitted from code

`guardedSave` and `guardedRefresh` contain completion guards, status transitions, and refresh/save conflict handling. They were omitted primarily for space, not because Marionette promises those behaviors. They are application responsibilities, not an identified API gap. Editor bindings, renderer/provider setup, and forwarding contracts were also omitted; their exact wiring remains unverified within my reading budget.

## 5. Alternatives

I considered View-owned persistence, but it conflicts with this editor's disposable lifetime. I would choose it for edits whose state and effects need not survive panel replacement. Observable collections could preserve more row identity than my plain-array replacement approach; I would choose them when row-local state or frequent incremental updates matters. `restart()` fits intentional feature replacement, but would destroy the editor during refresh.

## 6. Hardest statement to apply

Recollection: `material/docs/architecture.md`, **Clean up at the ownership boundary**, distinguishes automatic cleanup of destroyed Views from retained Application subscriptions after stop. Applying that requires tracking each source's lifetime. My omitted draft-store implementation leaves its final disposal insufficiently specified. That limitation is my assessment, not a documented Marionette defect or an explanation of another model's behavior.

## Stage: counterfactual

# Prompted counterfactual comparison

This comparison was explicitly requested after my designs; it is not evidence of a spontaneous initial choice.

**Marionette Application is the best fit for this task.** The feature has asynchronous readiness, an independent stop boundary, and effects that survive replaceable editors. A retained root View could hold drafts and requests while Regions manage its panels, but it would need custom feature activation and request invalidation. A plain controller could supply those policies, but would duplicate lifecycle and UI-ownership coordination already provided by Application.

Application removes custom initial-start cancellation/result suppression, root teardown coordination, and parent/child lifetime bookkeeping. Its prepared result connects readiness to activation. Registered child ownership lets the existing page survive stopping the library. It also provides an explicit retained instance across stop/start. It does not make arbitrary retained objects framework-disposable automatically.

Custom logic remains substantial: draft storage and observation; editor initialization and bounded status updates; per-document save serialization; preserving text typed after submission; errors and retries; refresh sequencing while retaining successful data; conflicts between refresh and save results; invalidating post-start completions; and reconciling remotely completed saves after feature stop. Application does not provide these request semantics.

**The prompt changed the exercise.** Asking for owners made lifetime boundaries explicit, which helped select a structure. The short code limit favored showing composition and lifecycle calls while moving difficult request policies into helpers and prose. A product implementation would need those helpers, actual event contracts, provider setup, and behavioral verification; the sketch does not establish their correctness.

**A View would suffice under simpler requirements:** the page supplies already-loaded documents, drafts may be discarded on editor closure, and saving is synchronous local-model editing with persistence owned elsewhere. Then a root View with list/editor Regions can own presentation without separate readiness or feature-request coordination.
